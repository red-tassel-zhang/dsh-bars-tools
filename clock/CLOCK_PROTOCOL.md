# 时钟协议

一份可执行的操作手册。看完这一段，任何一次触发都该知道先做什么。

## 1. 两种任务

| 类型 | 谁排的 | 用途 | 数量 |
|---|---|---|---|
| **时钟任务** | agent 自己 | 到点主动开口，演一小步 | 恰好一条 pending |
| **事件任务** | 用户指定 | 某个时刻做某件具体的事（如"两点整发文"） | 另计，不占上面那条 |

时钟任务和事件任务的提示词必须分开写。事件任务要带上下文摘要和第 0 步，否则触发那一刻只剩"演"。

## 2. 主循环

1. 跑 `python clock/biorhythm_clock.py --json`，取 `next`。
2. 用 `next` 建一条一次性任务，标题固定（例如「节律时钟」）。
3. 记下任务 id。
4. 到点触发：先跑第 0 步（见下），再演这一步，然后回到 1。
5. 用户在时钟响之前先说话：`--regen` 重抽，删旧任务，挂新任务。**不要**沿用旧的 `next`。

第 0 步：

```bash
python clock/watch_documents.py
```

输出里 `new` 或 `changed` 非空，先读文件再动笔。这是为了防止"没看文件就开始写"。

## 3. 用绝对时刻

建任务用绝对时间（`at` / `rrule` 的 DTSTART），不要用"多少秒之后"。相对时间会漂，而且和状态文件里的 `pending_wake_at` 对不上。

## 4. 校验

- `schedule_list` 里时钟任务恰好一条 pending。
- 状态文件的 `pending_wake_at` 等于任务的 `scheduledAt`（秒级）。
- 触发后 `--regen` 必须成功；失败就停排上报，**不手挑数字冒充随机**。

## 5. 失败处理

| 现象 | 处理 |
|---|---|
| 脚本起不来（如 `0xC0000142`） | 放宽执行权限重试一次 |
| 重试仍失败 | 停止排程，报告原因；不手挑时刻 |
| 输出乱码 | 设 `PYTHONIOENCODING=utf-8`；数值仍可信 |
| `next` 落在静默期 | 视为脚本异常，不建任务，上报 |
| 抽出的时刻已过 | 重抽，不要在过去的时刻上挂任务 |

## 6. 抽查

```bash
python clock/biorhythm_clock.py --curve      # 24 小时权重曲线
python clock/biorhythm_clock.py --simulate 300  # 跑 300 次看分布
```

如果分布明显偏斜，先怀疑种子或权重表，别怀疑调度器。

## 7. 一句话

> 用户抢话就重抽重挂；时钟响了就演一步、重抽、重挂；其余时间不开口。
